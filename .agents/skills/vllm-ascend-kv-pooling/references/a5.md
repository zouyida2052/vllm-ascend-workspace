# A5 无 standalone 池化

在 A5 启动或修复容器、核算池容量时读取。以下依据 Ascend950PR、memcache-hybrid/memfabric-hybrid 1.2.0 的实际验证；不代表所有镜像都需要同样修复。

先按 [UB/UBoE 协议与官方来源](a5-transports.md) 确认组网。下方 `device_urma` 是历史 UB 案例；明确 UBoE 时改用 `device_uboe`，并同步 HIXL 环境配置。叠加 PD 或 SSD 时读 [组合配方](pd-ssd.md)。

## 容器与设备

优先复用用户指定容器。需要创建或重建且已获授权时，结合当前 vllm-ascend 的 Ascend950DT/PR 容器指南与 workspace 的机器管理指导，核验主机上实际存在的设备与挂载：

- NPU 设备 `/dev/davinci*`、`/dev/davinci_manager`、`/dev/hisi_hdc`，A5 的 `/dev/ummu`、`/dev/uburma`；不要照搬主机不存在的 `/dev/devmm_svm`。
- 驱动、dcmi、npu-smi、Ascend 安装信息及实际需要的通信配置；模型和用户工作目录可达。使用已确认镜像，并记录不可变 image ID。
- 核验容器与主机发行版。一次 Ubuntu 镜像整体挂载 openEuler 主机 `/usr/lib64` 后，bash 提示 libtinfo 版本异常并以 135 退出；去掉整体覆盖后恢复。退出码 135 本身不是充分诊断依据。不要为补单个依赖覆盖整个系统库目录。
- 保留被替换容器及必要配置，确认旧容器可写层的数据用途；创建失败不删除备份。新容器检查 Python、torch/torch_npu 导入、设备数量，再在可用设备上做一次真实张量计算。
- 本次使用 host 网络、500GiB `/dev/shm` 上限和服务 `nofile=65535`。共享内存上限不等于预分配池容量；按任务需要选取，文件描述符上限在启动器/容器配置中持久化。

先核验目标 NPU 的现有进程。其他服务占卡时，报告具体服务及停机影响，只有在已有授权覆盖时才停止。先把新容器、配置、脚本准备好，再停止占卡服务；保留其命令和可验证进程身份。不要因停止一个 PD prefill 就扩大为停止 decode、proxy 或其他 Meta。

## 容量和启动配置

不创建或启动 standalone。以下是 UB 示例；UBoE 只在对应协议项使用 `device_uboe`，容量按实际进程数另行核算：

```ini
ock.mmc.meta_service_url = tcp://META_IP:META_PORT
ock.mmc.local_service.config_store_url = tcp://META_IP:CONFIG_STORE_PORT
ock.mmc.local_service.protocol = device_urma
ock.mmc.local_service.dram.size = 25GB
ock.mmc.local_service.max.dram.size = 1024GB
```

`25GB` 仅对应本次“整机 200GB、8 个存储 worker”的方案。读取 backend 初始化路径和原生日志确定实际分配 DRAM 的进程；TP、DP、PP 及 scheduler 客户端会影响进程数，不能仅按 DP 除容量。已验证版本 scheduler 使用 `init_bm=False`，不应再算一份 worker 的 DRAM。device_urma 的 DRAM 按 1GiB 对齐；核算 `进程数 × 对齐后的每进程容量`，为模型、系统及其他任务留出主存余量。`max.dram.size` 是上限，不代表当前已分配容量。

本次 8 条 `init bm success` 分别显示 `dram{26843545600}`、`hbm{0}`，合计 200GiB。配置文本已修改不等于注册容量已生效。

Meta 和 local 的地址/端口保持一致，分别显式传 `MMC_META_CONFIG_PATH`、`MMC_LOCAL_CONFIG_PATH`。若独立启动 Meta，核验业务、config store 和 metrics 端口均无冲突；不要修改其他服务使用的 Meta。顺序为 Meta → vLLM。

复用现场可运行的 A5 通信环境，例如经验证的 `ASCEND_LOCAL_COMM_RES`、`ASCEND_GLOBAL_RESOURCE_CONFIG`、业务网 IP/NIC 及 `PYTORCH_NPU_ALLOC_CONF`。这些是环境相关参数，不能硬编码其他主机的网卡或 IP。独立池化使用 AscendStoreConnector + `kv_both`；已有 PD 的 MultiConnector/`kv_producer` 不能原样作为独立服务配方。

## 真实生成暴露的兼容性问题

一个 2026-09-14 A5 Ubuntu 镜像中的 vLLM Ascend 调用 `inplace_partial_rotary_mul(..., negate_sin=True)`，健康检查通过后，首次生成仍因 `negate_sin is not supported on Ascend950` 失败。

现场同版本、已可运行容器的唯一相关差异是：把 `sin[:actual_tokens]` 改为 `-sin[:actual_tokens]`，去掉 `negate_sin=True`。它显式完成同一负号运算，不是关闭旋转位置编码。仅在确实复现同一错误、接口与参考实现匹配时考虑该兼容补丁；不能对每个 A5 镜像自动打补丁。备份原文件、保存 diff 和版本，明确报告这是源码兼容改动；修复后重新验证生成和池化。与参考环境有更多差异时继续定位，不能整目录复制包掩盖不兼容。

## 已验证结果的含义

本次 DeepSeek-V4-Flash FP8、DP8/TP1/EP8、MTP1、eager，关闭 HBM prefix cache，保留间隔 4096；没有为测试重新 editable 安装。eager 是复用的原启动方案，不是遇错后的降级。

- 独立短提示 smoke 成功。
- AISBench `input_len=8192, output_len=1, data_num=4, concurrency=1, repeat_rate=1.0, prefix_test, dp=8`。
- 8 条并发预热全部成功，外部命中 `0/66200`。
- 正式 4 条全部成功，实际输入各 8275 token，外部命中各 8192，总计 `32768/33100 = 98.997%`；平均 TTFT 1447.7ms。
- 正式请求落在 4 个 DP 域；其余域本阶段 0/0 表示无请求，不是命中失败。最终 `/health=200`，服务与 Meta 保持运行。

这些数字是验收口径示例，不是后续任务的预设输出或性能基线。按 [recipe.md](recipe.md) 保存本次真实结果。
